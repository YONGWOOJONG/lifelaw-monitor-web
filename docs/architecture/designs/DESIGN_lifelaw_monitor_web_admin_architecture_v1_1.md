## 1. 프로젝트 및 저장소 분리 목적

수집기 `lifelaw-monitor`는 배치 파이프라인이다. 관리자 Web은 상시 온라인
서비스다. 두 가지는 수명주기, 장애 반경, 보안 표면, 릴리스 주기가 모두 다르다.

분리하는 이유는 다음과 같다.

| 관점 | 분리하지 않을 때 | 분리할 때 |
|---|---|---|
| 수집기 복잡도 | 배치 저장소에 HTTP 서버·세션·RBAC·CSRF가 유입 | 배치는 CLI 단일 진입점 유지 |
| 릴리스 | UI 문구 수정에 배치 회귀 검증 전체 필요 | 독립 릴리스 |
| 장애 반경 | Web 취약점이 수집 자격증명까지 노출 | 런타임 계정·프로세스 분리 |
| 거버넌스 | 배치 저장소의 승인 절차에 UI 변경이 묶임 | 각자 권위 체계 |
| 보안 | 배치 계정이 인터넷에 노출되는 프로세스에 상주 | Web 전용 최소 권한 계정 |

참조 저장소는 D-20에서 `FastAPI·Frontend·API/Worker/Scheduler 물리 분리·MSA`를
현 Mode A 범위 밖으로 명시했고, 설계 종결 매트릭스에서도 이를
`CLOSED_OUT_OF_SCOPE`로 분류했다. **별도 저장소 구성은 그 결정을 뒤집는 것이
아니라, 그 결정이 지키려던 경계(수집기 범위 고정)를 유지한 채 관리 기능을
바깥에 두는 방식이다.** 수집기 저장소에는 여전히 FastAPI가 들어가지 않는다.

## 2. React + FastAPI 구조

> **A-02 확정 (2026-08-06).** 스택은 **FastAPI(Python) + React/TypeScript(Vite)**
> 로 확정한다. 검토한 대안과 기각 사유는 §2.1에 기록한다.

```text
┌──────────────────────────────────────────────┐
│ Browser — React + TypeScript (Vite)          │
│  라우팅 / 상태관리 / 폼 / 표 / 차트           │
└───────────────┬──────────────────────────────┘
                │ HTTPS, 세션 또는 토큰, CSRF 방어
┌───────────────▼──────────────────────────────┐
│ lifelaw-monitor-web  API — FastAPI (Python)  │
│  인증 · RBAC · DTO 검증 · 감사 · 명령 발행    │
└───────────────┬──────────────────────────────┘
                │ 최소 권한 DB 계정, DTO ↔ SQL 고정 매핑
┌───────────────▼──────────────────────────────┐
│ PostgreSQL (C 시스템)                         │
│  수집기 소유 테이블 + Web 소유 테이블         │
└───────────────▲──────────────────────────────┘
                │ 같은 DB, 다른 계정·다른 프로세스
┌───────────────┴──────────────────────────────┐
│ lifelaw-monitor — 배치 (CLI)                  │
│  수집 · 추출 · 정규화 · 비교 · 판정 · R 반영  │
└──────────────────────────────────────────────┘
```

- 프론트엔드와 API는 같은 저장소, **다른 배포 아티팩트**로 관리한다.
- 브라우저는 DB에 직접 접근하지 않는다.
- API는 ORM 모델을 그대로 노출하지 않고 DTO 경계를 둔다.

### 2.1 스택 결정 근거와 기각한 대안

**백엔드 계층 자체는 선택 사항이 아니다.** 다음 요구가 전부 서버에서만
성립하기 때문이다.

| 요구 | 근거 절 | 브라우저 단독 |
|---|---|---|
| `POLICY_BARRIER` advisory lock 아래 단일 트랜잭션 | §10 | 불가 |
| `expected_policy_version` 불일치 거부 | §20.1 | 불가 (클라이언트 우회 가능) |
| 일괄 변경 all-or-none 재검증 | §20.2 | 불가 |
| 기동 시 스키마 fail-closed 검증 | §21 | 불가 |
| 감사 append-only를 **DB 권한**으로 강제, 런타임 최소권한 계정 | §15·§19 | 불가 (브라우저에 자격증명 불가) |
| default-deny 인가 서버 검증 | §17.3 | 불가 |

**백엔드 언어가 Python이어야 하는 결정적 이유:** §10 규칙 1은 정책 변경을
수집기의 `set_site_policy()` / `set_target_policy()`와 동등한 트랜잭션 절차로
재현하거나 **공유 라이브러리로 추출해 호출**하도록 규정한다. 수집기가
Python이므로, 다른 언어를 택하면 공유 경로가 막히고 락 순서·이력 동기화·버전
증가를 손으로 재구현해야 한다. 그것은 §24.2가 "D-28 우회 없음"으로 판정한
전제를 실제로 무너뜨리는 드리프트 통로다.

기각한 대안:

| 대안 | 기각 사유 |
|---|---|
| 서버 렌더링 (Jinja2 + HTMX) | 기술적으로 성립하며 배포 아티팩트가 1개로 줄지만, 사용자가 React 기반 관리자 UI를 명시 요구했다. **기술적 결격이 아니라 요구사항 기준의 기각이다.** |
| Node/Next.js 풀스택 | 정책 변경 로직을 Python 공유 라이브러리로 재사용할 수 없다. 재구현은 D-28 드리프트 위험 |
| 기성 admin 도구 (Django admin 등) | 핵심 가치가 **범용 CRUD 자동 생성**인데 §6이 이를 정면 금지한다. 잠그고 나면 남는 이점이 없다 |

## 3. lifelaw-monitor와 HTTP API로 연결하지 않는 원칙

Web이 수집기를 HTTP로 호출하거나 그 반대 방향의 동기 호출을 만들지 않는다.

이유:

1. **가용성 결합 회피** — 배치가 내려가 있어도 관리 화면은 조회·정책 편집이
   가능해야 한다. 동기 호출은 배치 중단을 UI 장애로 전파한다.
2. **단일 작성자 유지** — HTTP 명령 경로가 생기면 Web이 상태를 직접 바꾸도록
   유혹받는다. 비동기 명령 원장은 그 유혹을 구조적으로 차단한다.
3. **배치 특성** — 수집기는 하루 한 번 도는 프로세스다. 상시 리스닝 포트를
   요구하는 것은 배치 모델과 맞지 않는다.
4. **공격 표면** — 배치 프로세스에 인바운드 포트를 열지 않는다.

대신 **관리 명령 Inbox**(§9)를 통해 비동기로 의도를 전달한다.

## 4. 실제 아키텍처 분류 — Shared Database Contract

이 구조의 정직한 이름은 **Shared Database / Integration Database** 패턴이다.
두 배포 단위가 하나의 PostgreSQL을 공유하고, 결합은 **스키마 계약**으로
이루어진다.

| 속성 | 이 설계에서의 실제 |
|---|---|
| 결합 지점 | 데이터베이스 스키마 |
| 결합 강도 | 중간~강함 (스키마 변경이 양쪽에 파급) |
| 통신 | 없음 (동기 호출 없음). 상태 전달은 테이블 |
| 트랜잭션 | 각자 로컬 트랜잭션. 분산 트랜잭션 없음 |
| 일관성 | 명령은 최종 일관성, 정책은 배리어로 직렬화 |

이 패턴의 알려진 약점과 대응:

- **약점: 스키마가 사실상 공용 API가 된다.** → §21 계약 버전 관리로 고정하고
  기동 시 fail-closed 검증한다.
- **약점: 두 시스템이 같은 행을 쓰면 경합한다.** → §6/§8 단일 작성자 원칙으로
  소유권을 분할한다.
- **약점: 스키마 변경 조율 비용.** → 소유권 표(§7)와 변경 절차(§21)로 통제한다.

## 5. 엄격한 MSA가 아니다

이 설계는 마이크로서비스가 아니다. 그렇게 부르지 않는다.

- 서비스별 독립 데이터베이스가 **없다** — MSA의 핵심 제약을 만족하지 않는다.
- 서비스 디스커버리, API 게이트웨이, 사가, 서킷 브레이커가 없다.
- 배포 단위는 2개뿐이고 조직 경계와 일치하지 않는다.

과대 명명은 실제 위험을 가린다. "MSA니까 독립적"이라고 가정하면 스키마 변경의
파급을 과소평가하게 된다. **두 배포 단위가 하나의 DB 계약에 강하게 묶여 있다는
사실을 설계의 전제로 유지한다.**

## 6. "모든 테이블 관리"의 정확한 정의

| 의미하는 것 | 의미하지 않는 것 |
|---|---|
| 모든 업무 데이터를 **조회**할 수 있다 | 모든 물리 테이블을 자유롭게 INSERT/UPDATE/DELETE 한다 |
| 필요한 **운영 행위**를 화면으로 제공한다 | 임의 SQL 또는 범용 CRUD 엔드포인트를 제공한다 |
| 상태를 **바꾸는 업무 명령**을 제공한다 | 상태 컬럼을 직접 편집한다 |
| Web이 **소유한** 데이터를 CRUD 한다 | 수집기가 소유한 데이터를 CRUD 한다 |

새 테이블이 추가되어도 관리자 UI에 자동 노출하지 않는다. 노출은 §7 표에
등록하는 명시적 행위여야 한다.

## 7. 테이블별 조회·CRUD·명령·불변 정책

### 7.1 수집기 소유 테이블 (참조 저장소 C1 / DDL 기준)

| 테이블 | 조회 | 쓰기 | 허용 행위 |
|---|---|---|---|
| `TC_COMMON_CODE` | 전체 | **금지** | 라벨 표시 전용. 코드 신설·수정·삭제·`use_yn` 변경 모두 금지 |
| `TN_CNPCLS_CNLNK` | 전체 | **금지** | R 마스터 사본. R1 동기화가 유일한 작성자 |
| `TN_CRAWL_TARGET` | 전체 | 정책 컬럼 **한정**, 명령 경유 | 실행 상태 컬럼 직접 수정 금지 |
| `TH_CRAWL_TARGET` | 전체 | **금지** | append-only 스냅샷. D-25 기준선 선택의 입력 |
| `TN_BATCH_RUN` | 전체 | **금지** | 실행 원장. 집계·상태는 R7 소유 |
| `TN_COLLECT_SITE_POLICY` | 전체 | 명령 경유 | §10 정책 명령으로만 변경 |

`TN_CRAWL_TARGET`에서 Web이 관여할 수 있는 것은 **대상 직접 정책**
(`target_collect_policy_cd`, `collect_target_kind_cd`, `target_policy_version`)
뿐이며, 그것도 직접 UPDATE가 아니라 §10 명령을 통한다.

**절대 쓰지 않는 컬럼:** `crawl_stat_cd`, `extract_stat_cd`, `norm_stat_cd`,
`cmpr_stat_cd`, `change_yn_cd`, `raw_html_hash`, `norm_html_hash`,
`prev_raw_hash`, `prev_norm_hash`, `crawl_diag_cd`, `crawl_candidate_url`,
`batch_ymd`, `file_*`.

**계산 컬럼:** `effective_collect_policy_cd`와 `execution_collect_policy_cd`는
DDL에서 `GENERATED ALWAYS AS ... STORED`다. Web은 **읽기만** 하고 값을 계산해
비교하거나 저장하지 않는다. 프론트엔드에서 OR 규칙을 재구현하면 드리프트가
생긴다.

### 7.2 Web 소유 테이블 (A-03·A-09 승인, 2026-08-06)

| 테이블 | 성격 | CRUD | 비고 |
|---|---|---|---|
| `TW_USER` | 계정 | C·R·U | 삭제는 비활성화로 대체 |
| `TW_ROLE`, `TW_PERMISSION`, `TW_ROLE_PERMISSION` | RBAC | C·R·U·D | §17 |
| `TW_USER_ROLE` | 사용자-역할 | C·R·D | |
| `TW_SESSION` | 세션 | C·R·D | A-04가 서버 측 세션으로 확정되어 **필수**다 |
| `TW_ADMIN_COMMAND` | 관리 명령 Inbox | C·R, 상태는 소비자가 전이 | §9 |
| `TW_APPROVAL` | 승인 원장 | C·R | §18 |
| `TW_AUDIT_LOG` | 감사 로그 | **C·R만** | append-only, §19 |

**A-09 확정.** 접두사는 `TW_`(Table, Web-owned)를 사용한다. 참조 저장소의
`TC_`/`TN_`/`TH_`와 충돌하지 않으며, 테이블명만 보고 소유 주체를 판별할 수 있다.
컬럼 명명은 참조 저장소 관행을 따른다 — 코드 컬럼은 `*_cd`, 시각은
`TIMESTAMPTZ(3)`, 등록·수정 시각은 `reg_dt`/`mod_dt`.

**소유 경계 불변식.** `TW_` 테이블은 Web이 유일한 작성자다. 수집기는 예외적으로
`TW_ADMIN_COMMAND`의 **상태 전이만** 수행한다(§9). 그 외 `TW_` 테이블에
수집기가 쓰지 않는다.

> **참조 저장소에 미치는 영향.** 참조 저장소는 D-26 확인 시점에 "영속
> PostgreSQL 사용자 테이블 없음"을 확정 사실로 기록했다. A-03 승인으로 그
> 사실은 더 이상 유효하지 않다. **같은 PostgreSQL 인스턴스에 `TW_` 테이블이
> 존재하게 되므로, 참조 저장소 쪽 문서에 이 사실을 반영할지는 그 저장소의
> 결정 사항이다.** 이 저장소에서 참조 저장소 문서를 수정하지 않는다.
> §23.2에 미결 항목으로 남긴다.

## 8. 단일 작성자 원칙

```text
정책 의도        Web  ──제출──▶  TW_ADMIN_COMMAND  ──소비──▶  수집기
실행 상태        수집기가 유일한 작성자
감사 기록        Web이 유일한 작성자 (append-only)
R 마스터 사본    R1 동기화가 유일한 작성자
```

예외는 하나다. **사이트·대상 수집 정책**은 Web이 승인된 명령 계약을 통해
직접 트랜잭션을 수행할 수 있다(§10). 이는 참조 저장소의 D-28 계약이 이미
"단일 트랜잭션 + 배리어 + 버전"으로 안전하게 정의해 두었기 때문이며, 그
계약을 그대로 호출하는 경우에만 허용한다.

## 9. 관리 명령 Inbox

Web은 상태를 바꾸는 대신 **의도를 기록**한다. 수집기가 자기 실행 주기에 그것을
읽어 수행한다.

```text
TW_ADMIN_COMMAND
  command_id        BIGINT   PK
  command_type      VARCHAR  RERUN_BATCH | CANCEL_BATCH | RESET_TARGET
                             | RESYNC_R_MASTER
  payload           JSONB    타입별 검증된 파라미터
  idempotency_key   VARCHAR  UNIQUE — 중복 제출 차단
  requested_by      VARCHAR  신청자
  requested_reason  VARCHAR  사유 (필수)
  approved_by       VARCHAR  승인자 (위험 등급에 따라 필수)
  status            VARCHAR  PENDING | ACCEPTED | REJECTED
                             | IN_PROGRESS | DONE | FAILED | EXPIRED
  expires_at        TIMESTAMPTZ(3)   만료 — 오래된 명령의 지연 실행 방지
  result_msg        VARCHAR
  reg_dt / mod_dt   TIMESTAMPTZ(3)
```

규칙:

- Web은 `PENDING` 행을 **INSERT만** 한다. 이후 상태 전이는 소비자(수집기)가
  수행한다. Web은 `REJECTED`(승인 거부)와 `EXPIRED`만 자기 권한으로 쓴다.
- `idempotency_key`로 중복 제출을 차단한다. 같은 키의 재제출은 기존 명령을
  반환하며 새 실행을 만들지 않는다.
- `expires_at`이 필요한 이유: 어제 신청한 `RERUN_BATCH`가 오늘 실행되면 안 된다.
  만료된 명령은 소비되지 않고 `EXPIRED`로 종료한다.
- 소비자는 아직 구현되지 않았다. **Inbox만 만들고 소비자가 없으면 명령은 영원히
  `PENDING`에 남는다.** UI는 이 상태를 "대기 중"이 아니라 "미처리(소비자 미구현)"로
  정직하게 표시해야 한다(§25 잔여 위험).

## 10. D-28 정책 변경과 POLICY_BARRIER

참조 저장소는 정책 변경을 다음으로 정의한다.

- 정책은 **사이트 상속**(`site_collect_policy_cd`)과 **대상 직접**
  (`target_collect_policy_cd`)으로 나뉘고, 최종값은 OR 규칙 계산 컬럼이다.
- `7010` 수집 / `7020` 수집제외. 상위 또는 하위 중 하나라도 `7020`이면 최종 제외.
- 변경은 **전역 배타 배리어**(PostgreSQL advisory lock) 아래 단일 트랜잭션에서
  수행하고, 같은 트랜잭션 안에서 하위 대상 재정합과 이력 동기화까지 끝낸다.
- 배치 실행은 **공유(shared)** 배리어를 잡는다. 즉 배치 실행 중 정책 변경은
  대기하거나 타임아웃된다.

Web API 설계 규칙:

1. **정책 테이블을 직접 UPDATE 하지 않는다.** 참조 구현의
   `set_site_policy()` / `set_target_policy()`와 동등한 트랜잭션 절차를
   그대로 재현하거나, 해당 로직을 공유 라이브러리로 추출해 호출한다.
   두 테이블을 따로 갱신하는 경로는 만들지 않는다.
2. 배리어 타임아웃은 **정상 동작**이다. HTTP 409 또는 503으로 매핑하고
   "배치 실행 중이라 정책을 변경할 수 없습니다. 잠시 후 다시 시도하세요"로
   안내한다. 재시도 버튼을 제공하고 자동 무한 재시도는 하지 않는다.
3. 사이트 host는 정규화(IDNA, 소문자) 후 **중복·상하위 포함 관계**를 검사한다.
   와일드카드와 URL 문법은 거부한다.
4. 대상 직접 정책은 종류 코드(`7110` 웹페이지 / `7120` PDF)와 링크 분류
   (`901001` / `901002`)의 일치를 강제한다.

## 11. 배치 fresh, resume, rerun

참조 저장소 R7/R2 기준.

| 모드 | 의미 | Web에서의 취급 |
|---|---|---|
| `fresh` | 해당 `batch_ymd`의 최초 신규 실행 | 표시 전용 |
| `resume` | 중단 지점부터 계속. 완료행 재처리 안 함 | 표시 전용 |
| `rerun` | **배치 전체 리셋 후 재수행** | 명령으로 신청, 고위험 |

- Web은 `TN_BATCH_RUN`의 `run_mode`나 `run_stat_cd`를 쓰지 않는다.
- `rerun`은 그날 수집된 결과를 전부 버리고 다시 도는 동작이다. 고위험(§18)으로
  분류하고 승인과 재인증을 요구한다.
- `slice` 강제 재기준선과 `resume`은 상호 배타다. UI는 이 조합을 아예 제출할 수
  없게 막는다.

## 12. 협력적 취소

R7은 마감 시각(참조 문서 기준 06:00)에 **cooperative cancellation**을 수행한다.
진행 중 작업은 새 행을 시작하지 않고, 임시 파일을 정리한 뒤 현재 항목을 종결한다.

Web의 취소 설계도 같은 모델을 따른다.

- 취소는 **요청**이다. 프로세스를 죽이지 않는다.
- `CANCEL_BATCH` 명령을 Inbox에 넣으면 수집기가 안전한 지점에서 관측하고 멈춘다.
- UI는 "취소됨"이 아니라 **"취소 요청됨 → 수집기 확인 대기 → 취소 완료"** 로
  단계를 구분해 보여준다. 즉시 취소된 것처럼 표시하면 거짓말이 된다.
- 강제 종료(kill) 버튼은 제공하지 않는다. 아티팩트 정합성과 락 해제를 깨뜨린다.

## 13. 개별 대상 재처리 reset bundle 필요성

**이것은 현재 존재하지 않는 기능이며 새 설계가 필요하다.**

확인한 사실: 참조 저장소 R2의 `rerun`은 **배치 전체** 리셋이다. 개별
`url_id` 하나만 되돌리는 경로가 없다. 그런데 운영에서 가장 흔한 요구는
"이 대상 하나만 다시 돌려주세요"다. 전체 rerun으로 대응하면 나머지 수백 건을
불필요하게 재수집하게 된다.

개별 재처리는 원자적으로 되돌려야 할 컬럼이 여러 개다. 이를 **reset bundle**로
정의한다.

```text
RESET_TARGET(url_id, batch_ymd) 이 원자적으로 되돌려야 하는 것
  crawl_stat_cd    → 1010 (대기)
  extract_stat_cd  → 2000 / 2010  (링크 종류에 따름)
  norm_stat_cd     → 3000 / 3010
  cmpr_stat_cd     → 4000 / 4010
  change_yn_cd     → 5000 (미확인)
  *_err_msg        → NULL
  crawl_diag_*     → NULL  (DDL CHECK 제약이 세 컬럼을 묶고 있음)
  raw/norm 해시    → NULL
  당일 TH 행       → 정합 유지 (append-only이므로 삭제 아님)
  기준선 컬럼      → 재선택 필요 (D-25 규칙 재적용)
```

이 묶음의 위험:

- 일부만 되돌리면 상태 머신이 불가능한 조합에 빠진다. 예를 들어
  `change_yn_cd`만 초기화하고 `cmpr_stat_cd`를 두면 판정 완료인데 결과가 없는
  행이 된다.
- `crawl_diag_cd` / `crawl_diag_msg` / `crawl_candidate_url`은 DDL CHECK가
  all-or-none으로 묶고 있어 부분 초기화 시 제약 위반이 난다.
- 기준선을 재선택하지 않으면 D-25 의미가 깨진다.

**결론:** reset bundle은 Web이 UPDATE로 구현할 대상이 **아니다.** 수집기 쪽에
`RESET_TARGET` 명령 소비자를 구현하고, 그 안에서 R2의 기준선 재선택을 재사용해야
한다. Web은 명령 제출과 결과 표시만 담당한다. 이 항목은 **수집기 저장소의 신규
설계·ADR을 필요로 한다**(§23).

## 14. 공통 코드 변경 제한

- `TC_COMMON_CODE`는 참조 저장소의 G1 정의를 물리화한 것이다. 코드값의 단일
  출처는 G1이며 DB는 사본이다.
- Web에서 코드 추가·수정·삭제·`use_yn` 토글을 **모두 금지**한다. 화면에는
  읽기 전용 조회만 제공한다.
- 라벨은 `code_nm`을 사용한다. 프론트엔드에 한글 라벨을 하드코딩하지 않는다.
- 화면 표시 라벨을 다르게 쓰는 것은 허용된다(예: 파일 행의 `5020`을
  "파일 변경됨"으로 표기). 단 **저장값은 불변**이고, 표시 매핑은 코드에
  주석과 함께 명시한다.
- 새 코드가 필요하면 그것은 Web의 결정이 아니라 G1 개정 사안이다. 중단하고
  보고한다.

## 15. 이력·감사 데이터 불변성

- `TH_CRAWL_TARGET`은 수집기 소유 append-only다. Web은 조회만 한다.
- `TW_AUDIT_LOG`는 Web 소유 append-only다. UPDATE/DELETE 경로를 코드에
  만들지 않고, **DB 권한에서도** 해당 계정에 UPDATE/DELETE를 부여하지 않는다.
  애플리케이션 레벨 규율만으로는 부족하다.
- 보존 정책상 삭제가 필요하면 그것은 운영 절차(파티션 드롭 등)이며 관리자
  UI 기능이 아니다.
- 참조 저장소는 `TH_CRAWL_TARGET`을 **현재 업무월 + 직전 2개월**만 보존한다
  (D-30). 따라서 3개월을 넘는 추이 조회 화면은 만들 수 없다. UI는 조회 가능
  범위를 명시하고 그 밖의 기간 선택을 비활성화한다.

## 16. CUBRID read-only 기본 정책

- CUBRID는 R 시스템 원장이다. 이 저장소는 **기본 read-only**다.
- 참조 저장소의 R1 Out-bound는 `R_CONTRACT_EVIDENCE` 활성화 게이트 아래 있고,
  HTTPS 진단 회신은 `R_HTTPS_DIAGNOSTIC_CONTRACT_EVIDENCE` 게이트 아래 있다.
  **두 게이트 충족 전 실제 write는 0건이어야 한다.**
- Web은 CUBRID 쓰기 경로를 구현하지 않는다. 필요해지는 순간 중단하고 보고한다.
- CUBRID 접속이 필요하더라도 endpoint만 설정에 두고 계정·비밀번호는 배포
  secret으로 주입한다. 설정 파일에 자격증명을 넣지 않는다.
- **등록 URL 자동 변경 금지:** 참조 저장소 D-32는 HTTPS 전환 후보
  (`crawl_candidate_url`)를 진단 정보로만 보존하고 R의 등록 URL을 자동으로
  바꾸지 않는다. UI는 후보 URL을 **표시만** 하고 "이 URL로 교체" 버튼을
  제공하지 않는다.

## 17. RBAC와 권한 목록

**default-deny.** 명시적으로 부여된 권한만 통과한다.

### 17.1 역할 (A-05 승인, 2026-08-06)

| 역할 | 설명 |
|---|---|
| `VIEWER` | 조회 전용 |
| `OPERATOR` | 조회 + 저위험 명령 신청 |
| `POLICY_MANAGER` | + 수집 정책 변경 |
| `APPROVER` | + 고위험 명령 승인 |
| `ADMIN` | + 계정·역할 관리 |
| `AUDITOR` | 조회 + 감사 로그 열람 (변경 권한 없음) |

`AUDITOR`를 `ADMIN`과 분리하는 이유는 감사 대상과 감사자를 같은 사람으로 두면
감사가 무의미해지기 때문이다.

### 17.2 권한 (A-05 승인, 2026-08-06)

아래 14개가 **확정된 전체 권한 집합**이다. 권한 문자열은 코드 상수로 고정하고,
새 권한 추가는 이 문서의 개정 사항이다. 임의 문자열을 권한으로 받지 않는다.

```text
target:read            대상 목록·상세 조회
target:history:read    이력 조회
batch:read             배치 실행 원장 조회
policy:read            정책 조회
policy:site:write      사이트 정책 변경
policy:target:write    대상 직접 정책 변경
command:rerun          배치 rerun 신청
command:cancel         배치 취소 신청
command:reset          개별 대상 재처리 신청
command:resync         R 마스터 재동기화 신청
command:approve        고위험 명령 승인
artifact:read          수집 아티팩트 열람
audit:read             감사 로그 열람
user:manage            계정·역할 관리
```

### 17.3 규칙

- 신청자와 승인자는 **같을 수 없다**(4-eyes). `command:approve`를 가진 사용자가
  자기 신청을 승인하는 것을 서버에서 거부한다.
- 프론트엔드의 메뉴 숨김은 인가가 아니다. **모든 검증은 서버에서** 한다.
- 아티팩트 열람은 원문 노출이므로 별도 권한으로 분리한다. `raw.bin`을 그대로
  내려주지 않고, PDF `diff.md`처럼 변경 부분만 담은 산출물을 우선 제공한다.

### 17.4 인증 방식 — 서버 측 세션 (A-04 확정, 2026-08-06)

인증은 **서버 측 세션 + 쿠키**로 확정한다. JWT와 사내 SSO는 채택하지 않는다.

기각 사유를 남긴다. JWT는 만료 전 **즉시 무효화가 어렵다.** 이 시스템은
`RERUN_BATCH` 같은 최고 위험 작업을 다루므로 "권한을 방금 회수했는데 토큰이
아직 산다"는 상태를 허용할 수 없다. §18 최고 등급의 재인증 요구와도 맞지 않는다.

확정 사항:

| 항목 | 결정 |
|---|---|
| 세션 식별자 | 서버 생성 난수(CSPRNG). 사용자 입력·추측 가능한 값 금지 |
| 저장 위치 | 서버 측. 구체 저장소는 A-03과 함께 결정 (§7.2 `TW_SESSION` 후보) |
| 쿠키 속성 | `HttpOnly`, `Secure`, `SameSite=Lax`, `Path=/` |
| 세션 데이터 | 쿠키에는 식별자만. 역할·권한을 쿠키에 넣지 않는다 |
| 권한 평가 시점 | **매 요청마다 서버에서 재조회.** 로그인 시점 스냅샷을 신뢰하지 않는다 |
| 유휴 만료 | 30분 (제안, 운영 확정 대상) |
| 절대 만료 | 12시간 (제안, 운영 확정 대상) |
| 로그아웃 | 서버 측 세션 즉시 파기. 쿠키 삭제만으로 끝내지 않는다 |
| 권한 변경 시 | 대상 사용자의 기존 세션을 무효화한다 |
| 재인증(§18 최고) | 비밀번호·MFA 재확인. 세션 재사용으로 대체하지 않는다 |

**A-02가 SPA(React)로 확정되었으므로 다음이 추가로 강제된다.**

1. **동일 출처 배포.** 프론트 정적 번들과 API를 같은 오리진에서 서비스한다
   (리버스 프록시로 `/` → 정적, `/api` → FastAPI). 쿠키 세션에 교차 출처를
   허용하면 `SameSite`를 완화해야 하고 CSRF 표면이 넓어진다.
2. **CORS는 기본 비활성.** 교차 출처 자격증명 요청(`credentials: include`)을
   허용하지 않는다. 개발 환경에서도 프록시로 동일 출처를 유지한다.
3. **CSRF 방어를 명시적으로 둔다.** `SameSite=Lax`만으로는 부족하다. 상태
   변경 요청(POST/PUT/PATCH/DELETE)에 CSRF 토큰을 요구하고 서버에서 검증한다.
   `Origin` 헤더 검증을 병행한다.
4. **인증 상태를 프론트엔드가 판단하지 않는다.** React는 서버가 내려준 권한
   목록으로 메뉴를 그릴 뿐이며, 이는 편의이지 인가가 아니다(§17.3).
5. **401과 403을 구분한다.** 401은 재로그인 유도, 403은 권한 부족 안내다.
   SPA가 403을 401로 오인해 로그인 화면을 띄우면 사용자가 원인을 오해한다.

## 18. 위험 등급별 승인

| 등급 | 예시 | 요구 사항 |
|---|---|---|
| 저 | 조회, 필터, 내보내기 | 권한만 |
| 중 | 대상 직접 정책 변경 | 권한 + 사유 |
| 고 | 사이트 정책 변경(하위 일괄 파급), `RESET_TARGET` | 권한 + 사유 + 승인 |
| 최고 | `RERUN_BATCH`, `RESYNC_R_MASTER`, 계정 권한 변경 | 권한 + 사유 + 승인 + **재인증** |

- 사이트 정책 변경이 고위험인 이유: 하나의 host 설정이 그 아래 **모든 대상**의
  상속값을 한 트랜잭션에서 바꾼다. 영향 범위가 사용자 예상보다 크다.
- 고위험 이상은 실행 전 **영향 미리보기**를 제공한다. "이 변경으로 N건이
  수집 제외됩니다"를 보여주고 확인받는다.
- 재인증은 세션 재사용이 아니라 비밀번호·MFA 재확인이다.

## 19. 감사 및 멱등성

### 19.1 감사

모든 변경에 대해 다음을 기록한다.

```text
TW_AUDIT_LOG
  audit_id, occurred_at, actor, actor_role, source_ip, user_agent
  action, target_type, target_id
  before_value JSONB, after_value JSONB
  reason, approval_id, idempotency_key, result
```

- **변경 전후 값**을 함께 남긴다.
- 실패한 시도도 남긴다. 권한 거부와 배리어 타임아웃도 감사 대상이다.
- 비밀번호·토큰·DSN은 마스킹한다.

**발견된 공백:** 참조 저장소의 `TN_CRAWL_TARGET`에는 `reger`/`moder` 컬럼이
없다(`reg_dt`/`mod_dt`만 존재). 사이트 정책 테이블에는 있다. 따라서 **대상
직접 정책 변경은 수집기 스키마 안에서 행위자 귀속이 불가능하다.** 대응:

- 1안 — Web의 `TW_AUDIT_LOG`가 행위자 원장을 담당한다. 수집기 스키마 변경 없음.
  단 DB만 보면 누가 바꿨는지 알 수 없다. **v0.1 제안은 1안이다.**
- 2안 — `TN_CRAWL_TARGET`에 행위자 컬럼을 추가한다. C1 스키마 MAJOR 변경이며
  참조 저장소의 ADR과 사용자 승인이 필요하다.

이 선택은 사용자 결정 사항이다(§23).

### 19.2 멱등성

- 모든 상태 변경 API는 `Idempotency-Key` 헤더를 받는다.
- 같은 키의 재요청은 새 부작용 없이 **최초 결과를 그대로 반환**한다.
- 키는 명령 테이블의 UNIQUE 제약으로 강제한다. 애플리케이션 체크만으로는
  동시 요청을 막지 못한다.

## 20. 낙관적 잠금과 일괄 변경 TOCTOU 방지

### 20.1 단건

참조 구현의 `set_target_policy()`는 `expected_policy_version`을 요구하고
불일치 시 거부한다. Web도 같은 규약을 따른다.

```text
GET  /api/targets/{url_id}   →  target_policy_version: 7
PUT  /api/targets/{url_id}/policy
     { collect_policy_cd: "7020", expected_policy_version: 7, reason: "..." }

버전 불일치 → HTTP 409 + 현재 값 동봉
```

UI는 409를 받으면 조용히 재시도하지 않는다. **현재 값과 사용자가 보던 값의
차이를 보여주고 다시 결정하게 한다.**

### 20.2 일괄 변경의 TOCTOU

"필터 결과 전체를 수집 제외" 같은 기능은 위험하다. 필터 조회 시점과 실행
시점 사이에 대상 집합이 달라질 수 있다(TOCTOU).

방어:

1. **필터를 그대로 실행하지 않는다.** 조회 결과의 `url_id` 목록과 각 행의
   `target_policy_version`을 **명시적으로 제출**받는다.
2. 서버는 배타 배리어 아래에서 전체 목록의 버전을 재확인한다.
3. **하나라도 불일치하면 전부 거부한다(all-or-none).** 부분 적용은 사용자가
   무엇이 바뀌었는지 알 수 없게 만든다.
4. 일괄 변경 상한(예: 200건)을 두고, 초과 시 거부하고 범위를 좁히게 한다.
5. 실행 전 영향 미리보기와 확인 절차를 요구한다(§18).

## 21. 저장소 간 DB 계약 버전 관리

두 저장소가 하나의 스키마에 의존하므로 계약을 명시적으로 고정한다.

```text
docs/contracts/db-contract.md   (제안)
  참조 대상        : lifelaw-monitor
  참조 문서/버전   : C1 v2.20, DDL create_c_schema_v2_19.sql
  코드 정의        : G1 v3.14
  의존 테이블      : TC_COMMON_CODE, TN_CNPCLS_CNLNK, TN_COLLECT_SITE_POLICY,
                     TN_CRAWL_TARGET, TH_CRAWL_TARGET, TN_BATCH_RUN
  의존 계산 컬럼   : effective_collect_policy_cd, execution_collect_policy_cd
  의존 코드값      : 1010/1020/1090, 5000/5001/5010/5020/5030/5040,
                     6010~6090, 7010/7020, 7110/7120, 8010/8020,
                     901001/901002
```

**fail-closed 규칙:**

- API 기동 시 실제 스키마를 검증한다. 기대 테이블·컬럼이 없거나, 계산 컬럼이
  `STORED GENERATED`가 아니거나, 기대 코드값이 `TC_COMMON_CODE`에 없으면
  **해당 기능을 열지 않고 기동을 실패시킨다.** 참조 구현에도 동등한
  `validate_schema()` 절차가 있으므로 같은 엄격도를 유지한다.
- 조용한 폴백(컬럼 없으면 NULL 취급 등)을 만들지 않는다. 드리프트를 숨긴다.
- 수집기 쪽 C1이 개정되면 이 문서의 버전 핀을 갱신하고 영향 검토를 거친다.
  버전 핀 갱신 없이 새 컬럼에 의존하지 않는다.

| `Implementation-Authority=true`가 **미승인 항목까지** 권위를 주는가 | **수정함** | v0.1은 전 항목이 `false`라 문제가 없었으나, 승격으로 `TW_*` 테이블·역할·권한 목록까지 권위를 얻는 것처럼 읽힐 수 있었다. 상단 배너에 승인/미승인 범위를 분리하고 §23.1을 승인 상태의 단일 출처로 선언 |
| 세션 채택이 §18 재인증 요구와 모순되는가 | 통과 | §17.4에서 재인증을 세션 재사용으로 대체하지 않음을 명시 |
| SPA + 쿠키 세션이 CSRF 표면을 넓히는가 | **수정함** | `SameSite=Lax`만 믿는 설계였다면 취약. §17.4에 동일 출처 배포·CORS 기본 비활성·CSRF 토큰·`Origin` 검증을 강제 조항으로 추가 |
| 로그인 시점 권한 스냅샷으로 권한 회수가 지연되는가 | **수정함** | §17.4에 "권한은 매 요청 서버 재조회", "권한 변경 시 기존 세션 무효화" 추가 |
| A-04 승인이 A-03 미승인 상태에서 구현 가능한가 | **수정함** | 세션 저장 매체가 `TW_SESSION`(A-03 대상)에 종속됨을 놓치고 있었다. §23.1에 종속 관계와 "A-03 전 세션 영속화 미구현"을 명시 |
| 스택 확정이 §24.2의 D-28 통과 판정을 약화시키는가 | 통과 | 오히려 강화. §2.1에서 Python 고정이 §10 공유 라이브러리 경로의 전제임을 근거로 기록 |
| 단계 계획이 미승인 항목에 의존하는 단계를 "착수 가능"으로 표시하는가 | **수정함** | §22에 상태 열을 추가하고, 어느 승인에도 종속되지 않는 1단계만 착수 가능으로 한정 |
| v0.1과 v1.0이 동시에 활성으로 읽히는가 | **수정함** | v0.1 헤더를 `SUPERSEDED`로 변경하고 후계를 명시. `docs/README.md` 문서 목록도 갱신 |

## 부록. 참조한 공개 계약 요약

> 아래는 `lifelaw-monitor`의 활성 공개 문서에서 확인한 **사실**이며, 이 문서의
> 제안과 구분한다. 사본이므로 원본이 개정되면 이 요약은 무효가 된다.

**테이블 6개:** `TC_COMMON_CODE`, `TN_COLLECT_SITE_POLICY`, `TN_CNPCLS_CNLNK`,
`TN_CRAWL_TARGET`, `TH_CRAWL_TARGET`(월별 RANGE 파티션), `TN_BATCH_RUN`

**상태 코드:**

```text
CRAWL_STAT     1010 대기 / 1020 성공 / 1090 실패
EXTRACT_STAT   2000 비대상 / 2010 대기 / 2020 성공 / 2090 실패
NORM_STAT      3000 비대상 / 3010 대상 / 3020 성공 / 3090 실패
CMPR_STAT      4000 비대상 / 4010 대상 / 4020 완료
CHANGE_YN      5000 미확인 / 5001 기준선 설정 / 5010 변경없음
               5020 원본 변경 / 5030 상세내용 변경없음 / 5040 상세내용 변경됨
RUN_STAT       6010 대기 / 6020 실행중 / 6030 정상 / 6040 부분성공
               6080 취소 / 6090 실패
COLLECT_POLICY 7010 수집 / 7020 수집제외
TARGET_KIND    7110 웹페이지 / 7120 PDF
CRAWL_DIAG     8010 HTTPS 전환 후보 / 8020 URL 이전 후보
LINK_CLASS     901001 웹사이트 / 901002 첨부파일
```

`5001`은 신규 등록·강제 재기준선·성공 기준선 부재를 포함한다. **변경 감지
건수에 합산하면 안 된다.**

**시간:** 12개 instant는 `TIMESTAMPTZ(3)`, `batch_ymd`는 서울 업무일자
`CHAR(8)`. 지역시각 provenance는 `Asia/Seoul`.

**아티팩트 경로:** `/{artifact_root}/{batch_ymd}/{url_id}/raw.bin`.
PDF 2차 비교 시 같은 경로에 `extraction.json`(F4 소유),
`normalization.json`(R5 소유), `diff.md`(5040에서만 생성).
