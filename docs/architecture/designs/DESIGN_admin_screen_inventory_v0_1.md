# 관리자 Web 화면 목록 (G-2) — v0.1

> **이 문서는 `PROPOSAL`이며 구현 권위가 아니다.** 화면 목록은 API 계약의
> 입력이므로, 이 문서가 승인되기 전에는 엔드포인트와 DTO를 확정하지 않는다.
>
> 상위 권위는 `DESIGN_lifelaw_monitor_web_admin_architecture_v1_2.md`이며,
> 충돌 시 상위 문서가 우선한다. 특히 승인 상태는 상위 문서 §23.1이 단일
> 출처다.

---

## 1. 목적

사용자 요구는 "DB 테이블 정보를 화면에 표시하거나 CRUD 하는 웹"이다. 이를
상위 설계 §6의 정의에 맞춰 **구체적인 화면 단위로 분해**한다.

상위 설계 §6은 "모든 테이블 관리"를 이렇게 규정했다.

- 모든 업무 데이터를 **조회**할 수 있다
- 필요한 **운영 행위**를 화면으로 제공한다
- 상태는 **업무 명령**으로 바꾼다. 상태 컬럼을 직접 편집하지 않는다
- **Web이 소유한** 데이터만 CRUD 한다

따라서 화면은 테이블 하나에 CRUD 화면 하나가 붙는 구조가 아니다. **조회 화면은
테이블을 따라가고, 쓰기 화면은 업무 행위를 따라간다.**

## 2. 설계 원칙

1. **화면은 명시적 등록물이다.** 새 테이블이 생겨도 자동으로 화면이 생기지
   않는다(상위 §6). 이 문서의 표에 추가하는 것이 등록 행위다.
2. **읽기 화면과 쓰기 화면을 분리한다.** 조회 중 실수로 상태를 바꾸는 경로를
   만들지 않는다.
3. **쓰기는 전부 명시적 행위 화면을 거친다.** 목록 그리드의 인라인 편집을
   제공하지 않는다.
4. **위험 등급이 올라갈수록 단계를 늘린다.** 사유 입력 → 영향 미리보기 →
   승인 → 재인증(상위 §18).
5. **프론트엔드의 메뉴 숨김은 인가가 아니다.** 서버가 매 요청 검증한다
   (상위 §17.3·§17.4).

## 4. 주요 화면 상세

### S-03 운영 현황 대시보드

오늘 업무일자(`batch_ymd`, 서울 기준) 기준 요약.

- 배치 실행 상태 — `run_stat_cd` (6010 대기 / 6020 실행중 / 6030 정상 /
  6040 부분성공 / 6080 취소 / 6090 실패)
- 단계별 진행 — 수집·추출·정규화·비교 각 상태 코드 집계
- 변경 감지 — 5020 원본 변경, 5040 상세내용 변경됨
- 실패 — 1090 / 2090 / 3090
- 대기 중 관리 명령 수

> **집계 규칙 (중요).** `5001`(기준선 설정)은 신규 등록·강제 재기준선·성공
> 기준선 부재를 포함한다. **변경 감지 건수에 합산하지 않는다.** 합산하면 신규
> 대상이 대량 등록된 날 변경 건수가 폭증한 것처럼 보인다.

### S-04 수집 대상 목록

필터: 업무일자, 사이트(host), 링크 분류(901001 웹사이트 / 901002 첨부파일),
대상 종류(7110 웹페이지 / 7120 PDF), 각 단계 상태 코드, 변경 여부 코드,
최종 수집 정책(`execution_collect_policy_cd`).

- 정렬·페이징은 서버 측. 전체 건수는 별도 조회로 분리(대용량 `COUNT` 회피)
- 계산 컬럼 `effective_collect_policy_cd` / `execution_collect_policy_cd`는
  **읽기 전용으로 표시만** 한다. 프론트엔드에서 OR 규칙을 재구현하지 않는다
  (상위 §7.1)
- 각 행에 `target_policy_version`을 함께 내려준다. S-09 일괄 변경의 입력이다
- **인라인 편집 없음**

### S-05 수집 대상 상세

- 현재 상태 4종 + 변경 여부, 진단 코드(8010 HTTPS 전환 후보 / 8020 URL 이전 후보)
- 해시(`raw_html_hash`, `norm_html_hash`, `prev_*`)는 **표시 전용**
- `crawl_candidate_url`은 **표시만 한다. "이 URL로 교체" 버튼을 제공하지
  않는다**(상위 §16, 참조 저장소 D-32)
- 아티팩트 링크 → S-07

### S-06 대상 변경 이력

`TH_CRAWL_TARGET` 조회. 월별 RANGE 파티션.

> **보존 제약.** 참조 저장소 D-30은 **현재 업무월 + 직전 2개월**만 보존한다.
> 기간 선택 UI는 조회 가능 범위를 명시하고 그 밖의 기간을 **비활성화**한다.
> "데이터가 없습니다"로 처리하면 사용자가 유실로 오해한다.

### S-08 사이트 정책 관리 — 고위험

`TN_COLLECT_SITE_POLICY`의 `site_collect_policy_cd`(7010 수집 / 7020 수집제외).

절차: 대상 host 선택 → **영향 미리보기**("이 변경으로 N건이 수집 제외됩니다")
→ 사유 입력 → 승인 → 실행.

- 호스트는 정규화(IDNA, 소문자) 후 **중복·상하위 포함 관계**를 검사한다.
  와일드카드와 URL 문법은 거부한다(상위 §10)
- 실행은 D-28 `POLICY_BARRIER` 계약을 그대로 호출한다. Web이 정책 테이블과
  하위 상속값을 따로 갱신하는 경로를 만들지 않는다
- **배리어 타임아웃은 정상 동작이다.** HTTP 409/503 → "배치 실행 중이라 정책을
  변경할 수 없습니다. 잠시 후 다시 시도하세요" + 재시도 버튼. 자동 무한 재시도
  금지(상위 §10)

### S-09 대상 직접 정책 변경

단건과 일괄 두 경로. 단건은 `expected_policy_version`을 동봉하고, 409 응답 시
**조용히 재시도하지 않고 현재 값과의 차이를 보여준다**(상위 §20.1).

일괄 변경은 TOCTOU 방어가 필수다(상위 §20.2).

1. 필터를 그대로 실행하지 않는다. `url_id` 목록과 행별 `target_policy_version`을
   **명시 제출**받는다
2. 서버가 배타 배리어 아래에서 전 건 버전을 재확인한다
3. **하나라도 불일치하면 전부 거부한다(all-or-none)**
4. 상한 200건. 초과 시 거부하고 범위를 좁히게 한다
5. 실행 전 영향 미리보기와 확인

또한 대상 종류 코드(7110/7120)와 링크 분류(901001/901002)의 일치를 강제한다.

### S-12 배치 제어

- **rerun — 최고 위험.** 그날 수집 결과를 전부 버리고 다시 돈다. 권한 + 사유 +
  승인 + **재인증**
- **cancel — 협력적 취소.** 프로세스를 죽이지 않는다. 표시는 3단계로 구분한다:
  **"취소 요청됨 → 수집기 확인 대기 → 취소 완료"**. 즉시 취소된 것처럼 표시하면
  거짓말이 된다(상위 §12)
- `slice` 강제 재기준선과 `resume`은 상호 배타다. **UI가 이 조합을 아예 제출할
  수 없게 막는다**(상위 §11)
- Web은 `TN_BATCH_RUN`의 `run_mode`·`run_stat_cd`를 쓰지 않는다. 명령만 넣는다

### S-14 관리 명령 목록·상세

> **정직성 요구.** 명령 소비자(수집기 측)가 구현되기 전까지 명령은 영원히
> `PENDING`에 남는다. UI는 이를 "대기 중"이 아니라 **"미처리 (소비자 미구현)"**
> 로 표시한다(상위 §9·§25 R-02). 진행 중인 것처럼 보이게 하지 않는다.

### S-17 공통 코드 조회 — 읽기 전용

`TC_COMMON_CODE`는 참조 저장소 G1 정의의 물리화 사본이다.

- 추가·수정·삭제·`use_yn` 토글을 **모두 제공하지 않는다**(상위 §14)
- 라벨은 `code_nm`을 쓴다. 프론트엔드에 한글 라벨을 하드코딩하지 않는다
- 표시 라벨을 다르게 쓰는 것은 허용하되(예: 파일 행의 5020을 "파일 변경됨"),
  저장값은 불변이고 매핑은 코드에 주석과 함께 명시한다

### S-20 감사 로그 조회 — append-only

- 조회·필터·내보내기만. **수정·삭제 UI를 만들지 않는다**
- DB 권한에서도 런타임 계정에 UPDATE/DELETE를 부여하지 않는다(상위 §15)
- 실패한 시도(권한 거부, 배리어 타임아웃)도 조회 대상이다
- `AUDITOR`는 `ADMIN`과 분리한다. 감사 대상과 감사자가 같으면 감사가 무의미해진다

### S-21 계약·스키마 상태

기동 시 fail-closed 검증(상위 §21)의 결과를 표시한다. 기대 테이블·컬럼,
계산 컬럼의 `STORED GENERATED` 여부, 기대 코드값 존재 여부, 고정된 계약 버전
핀(C1 v2.20 / DDL v2.19 / G1 v3.14).

**이 화면은 어떤 미승인 항목에도 종속되지 않는다.** 1단계 산출물의 가시화이며
가장 먼저 만들 수 있다.

## 6. 제공하지 않는 화면 — 명시적 금지 목록

요구가 들어와도 만들지 않는다. 이유를 함께 남긴다.

| 만들지 않는 것 | 이유 |
|---|---|
| 관리자용 SQL 실행기 / 쿼리 콘솔 | 상위 §6 — 범용 SQL 입력 API 금지 |
| 테이블 범용 CRUD 화면(테이블명 파라미터) | 상위 §6 — 범용 테이블명 입력 금지 |
| 상태 코드 직접 편집 화면 | 상위 §7.1 — 실행 상태는 수집기 소유 |

| 이력·감사 수정/삭제 화면 | 상위 §15 — append-only |
| 배치 강제 종료(kill) 버튼 | 상위 §12 — 아티팩트 정합성·락 해제를 깨뜨림 |
